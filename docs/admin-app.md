# THE_X Admin ในแอป

## จัดการผู้ใช้และร้าน

ในแท็บผู้ใช้ Admin ค้นหาด้วยชื่อ อีเมล หรือเบอร์โทร แล้วแก้ชื่อผู้ใช้ ชื่อ นามสกุล อีเมล โทรศัพท์ บทบาท และสถานะบัญชีได้ เมนูรถในโรงรถใช้แก้รายละเอียดรถของลูกค้าได้ การเปลี่ยนข้อมูลสำคัญถูกบันทึกในประวัติกิจกรรม Admin; การเปลี่ยนอีเมลจะล้างสถานะยืนยันอีเมลเดิมเฉพาะเมื่ออีเมลเปลี่ยนจริง ระบบไม่ส่งรหัสผ่านหรือ API key ผ่านรายการผู้ใช้

ในแท็บร้านบริการ Admin ค้นหาร้านแล้วแก้ชื่อ ที่อยู่ โทรศัพท์ คำอธิบาย รูป หมุดแผนที่ สถานะรับจอง และช่างประจำร้านได้ สถานะกำกับร้านแยกจากปุ่มเปิดรับจองของเจ้าของร้าน:

- **ระงับชั่วคราว:** ต้องระบุเหตุผลและเวลาสิ้นสุด ร้านถูกซ่อนและรับการจอง/ข้อความใหม่ไม่ได้จนถึงเวลานั้น จากนั้นกลับมาใช้งานอัตโนมัติ
- **แบน:** ต้องระบุเหตุผล ร้านถูกซ่อนต่อเนื่องจนกว่า Admin จะคืนสถานะ
- **ซ่อนถาวร:** ต้องระบุเหตุผล ร้านไม่ปรากฏในแอปและแก้ไขหรือคืนสถานะไม่ได้ แต่แถวร้าน งานซ่อม และแชตเดิมยังอยู่เพื่อให้ผู้เกี่ยวข้องดูประวัติ
- **คืนสถานะ:** ใช้ได้กับร้านที่ระงับหรือแบน โดยไม่เปลี่ยนการตั้งค่ารับจองของร้าน

เมื่อร้านถูกระงับหรือซ่อน ลูกค้าและช่างยังอ่านงานจองและแชตย้อนหลังได้ แต่สร้างการจองหรือแชตใหม่ ส่งข้อความใหม่ และรับ/เริ่มงานซ่อมใหม่ไม่ได้ งานที่กำลังซ่อมสามารถปิดงานได้เพื่อเก็บประวัติให้ครบ การค้นหาแสดงสูงสุด 100 ผลลัพธ์ต่อคำค้น; ค้นให้แคบลงหากมีข้อมูลมากกว่านั้น

## รายละเอียดการจองและข้อมูลฐานข้อมูล

แท็บการจองค้นหาจากหมายเลข ลูกค้า ร้าน รถ หรือสถานะได้ กดรายการเพื่อดูข้อมูลผู้เกี่ยวข้อง รถ ร้าน ช่าง เวลานัด อาการ บันทึกซ่อม เหตุผลยกเลิก และประวัติการเปลี่ยนสถานะ Admin แก้ไขเวลานัด อาการ และบันทึกซ่อมได้โดยมี audit; การเปลี่ยนสถานะทำผ่านคำสั่งยกเลิกพร้อมเหตุผล ไม่แก้ช่อง status ตรงๆ รายการที่ปิดหรือยกเลิกแล้วซ่อนจากแอปได้โดยเก็บแถวและประวัติไว้

แท็บฐานข้อมูลแสดงตารางทั้งหมดใน **ฐานข้อมูล Django หลัก** รวม auth/OIDC และตารางระบบ หน้าละ 30 แถว โดยไม่รับ SQL จากผู้ใช้และไม่ส่งค่า password, token, private key, session data หรือ credential ออก API ตารางธุรกิจเปิดเครื่องมือจัดการตามชนิดข้อมูล: ผู้ใช้ ร้าน รถ การจอง ข้อมูลความรู้ ห้องแชต ข้อความ แจ้งเตือน และประวัติ AI การซ่อนรถ ห้องแชต หรือบทสนทนา AI เก็บแถวเดิมไว้; ข้อความที่ redacted แสดงข้อความแทนในแอปแต่เก็บต้นฉบับให้ Admin ตรวจสอบ โทเค็น OIDC เพิกถอนได้พร้อมเหตุผล

ตาราง auth/OIDC อื่นและ audit เป็นแบบอ่านอย่างปลอดภัย ไม่เปิดแก้ไข/ลบแถวตรง เพราะจะข้ามการตรวจสิทธิ์ ทำให้การเข้าสู่ระบบเสีย หรือทำลายหลักฐานการเปลี่ยนแปลง ฐาน n8n และฐาน AI vector เป็น PostgreSQL แยกจาก Django จึงไม่ได้อยู่ในตารางของแท็บนี้ การเปลี่ยนข้อมูลความรู้ที่มี embedding ให้ใช้เครื่องมือเฉพาะซึ่งลบเวกเตอร์เก่าก่อนรอทำ embedding ใหม่

Admin เข้าผ่านหน้า login/OIDC เดียวกับผู้ใช้ทั่วไป แล้ว Flutter ส่งไปที่ `/admin-dashboard` ตามบทบาทจาก Django. `/admin/` ของ Django ยังใช้เป็นทางสำรองสำหรับงานเฉพาะที่ UI นี้ยังไม่มี.

หน้า Admin มีภาพรวม, ผู้ใช้/บทบาท, ร้าน/สมาชิกช่าง, รายการการจอง, ฐานความรู้รถสำหรับ AI, และประวัติกิจกรรม Admin. API ทุกเส้นทาง `/api/admin/*` ตรวจ OIDC bearer token และ `is_superuser` ฝั่ง Django. การเปลี่ยนบทบาทใช้กติกาเดียวกับ Django admin: ต้องเหลือ Admin ที่ใช้งานได้อย่างน้อยหนึ่งคน และห้ามเปลี่ยนบทบาทช่างที่มีงานซ่อมกำลังทำ. การถอดช่างจากร้านถูกปฏิเสธหากช่างมีงานที่รับหรือกำลังซ่อมในร้านนั้น.

## ความรู้รถและ embedding

แท็บฐานความรู้ AI แสดง **passages ที่ n8n PGVector Store ค้นหาได้จริง** จากฐาน `the_x_ai_vectors.the_x_manual_vectors` แยกจากรายการ `MotorcycleKnowledge` ที่ Admin เพิ่มผ่าน Django. รายการ PGVector ค้นหารุ่น/เนื้อหาและเปิดอ่านทั้งหมดแบบแบ่งหน้า 20 รายการ จึงเห็น Honda BigWing 95 passages ที่นำเข้าไว้แล้ว. แก้ไขหัวข้อ รุ่น ปี และ URL ได้; ถ้าแก้เนื้อหาต้องมี Gemini Embedding API key ใน Admin เพื่อสร้างเวกเตอร์ใหม่ก่อนบันทึก. ทุกการแก้ไขเก็บเวอร์ชันเดิมใน `the_x_manual_vector_history`; การลบต้องระบุเหตุผลและย้ายเวกเตอร์ออกจากตารางที่ AI ค้นหา โดยยังเก็บประวัติไว้. สคริปต์นำเข้า BigWing จะไม่เขียนทับรายการที่ Admin แก้ไขหรือลบไว้. รายการที่เพิ่มจาก Django ต้องจัดการในส่วน `ข้อมูลที่ Admin เพิ่มเอง` เพื่อให้ต้นฉบับและเวกเตอร์ตรงกัน; การลบจะซ่อนแถว Django และถอนเวกเตอร์ออก แต่เก็บประวัติและเหตุผล. นี่คือข้อมูลที่ระบบ RAG *ค้นหาได้* ไม่ใช่ความรู้ทั่วไปทั้งหมดในโมเดล Gemini.


ข้อมูลที่เพิ่มในหน้านี้เป็นสเปก/ข้อเท็จจริงที่มี URL ต้นทาง ไม่ใช่รถส่วนตัวของลูกค้า. Admin ต้องตรวจข้อมูลและสิทธิ์ใช้ก่อนกด embedding. API ส่งข้อความไปยัง Gemini `models/gemini-embedding-001` แล้ว upsert ลง `the_x_ai_vectors.the_x_manual_vectors` ที่ n8n PGVector Store เดิมใช้อยู่. ขนาดเวกเตอร์คือ 3072 และ id คงที่ต่อรายการเพื่อให้กดซ้ำได้โดยไม่เพิ่มแถวซ้ำ. การแก้ไขรายการที่ embed แล้วลบเวกเตอร์เดิมและเปลี่ยนสถานะเป็นรอ embedding ใหม่.

ตั้ง Gemini **Embedding** API key ในแท็บฐานความรู้ AI. Backend เข้ารหัสคีย์ด้วยกุญแจที่แยกตามบริบทจาก `DJANGO_SECRET_KEY`; API ส่งกลับเพียงสถานะและ 4 ตัวท้าย. ต้องรักษา `DJANGO_SECRET_KEY` ให้คงเดิมระหว่าง restart และเก็บสำรองอย่างปลอดภัย เพราะเปลี่ยนแล้วจะถอดรหัส API key เดิมไม่ได้. คีย์นี้ยังไม่เปลี่ยน Chat Model credential ใน n8n; การจัดการ n8n อยู่ในรอบถัดไป. หากคีย์เคยถูกส่งผ่านแชตหรือเปิดเผย ให้หมุนคีย์ก่อนใช้จริง.

รันชุด local Docker ที่มี AI database ด้วย PowerShell จาก root โปรเจกต์:

```powershell
docker compose --env-file deploy/.env -f compose.deploy.yaml -f compose.ai.yaml up -d --build --wait init backend web
```

คำสั่งนี้รัน migration และ rebuild เว็บ/Backend ใน Docker ที่ใช้อยู่; ไม่ลบข้อมูล PostgreSQL. หากยังไม่มี AI database ให้เตรียมตาม `docs/ai-rag-database.md` ก่อน. สำหรับการทดสอบไม่ใช้ Docker:

```powershell
uv run --directory backend --python 3.12 python manage.py test garage --settings=the_x.test_settings
Push-Location frontend
& 'D:\flutter\bin\flutter.bat' analyze --no-pub
& 'D:\flutter\bin\flutter.bat' test --no-pub --concurrency=1
Pop-Location
```

ขอบเขตปัจจุบัน: ร้านและการจองแสดงเพื่อดูภาพรวม; เจ้าของร้านยังควบคุมการรับจองเอง. ข้อมูลความรู้เพิ่ม/แก้ทีละรายการ ส่วนการนำเข้าจำนวนมากยังใช้สคริปต์ ingest. ผลตอบ AI จริงยังขึ้นกับ n8n workflow/credential และแหล่งข้อมูลที่ตรวจแล้ว; การผ่าน unit tests ไม่เท่ากับผ่าน live RAG end-to-end.
