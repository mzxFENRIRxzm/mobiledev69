# THE_ONE prototype → ข้อมูลอ้างอิงสำหรับ THE_X

อ่านเมื่อ 26 กันยายน 2026 จากเอกสาร Google Docs ชื่อ `THE_ONE.docx` ที่ผู้ใช้ส่งในบทสนทนา ซึ่งเป็นรายงาน “ระบบแชทบอทและจองคิวซ่อมสำหรับรถจักรยานยนต์ THE_ONE” ผู้ใช้ระบุให้ใช้เป็น **prototype ของ THE_X** ควบคู่กับ [โค้ด THE_ONE ที่เคยอ้างอิง](https://github.com/zxSUPHASANxz/THE_ONE_FINAL/tree/f4db01a) เอกสารนี้สรุปพฤติกรรมและแนวคิดจากต้นแบบ ไม่ใช่การยืนยันว่า THE_X ต้องคัดลอกทุกเทคโนโลยีหรือทุก flow ตามตัวอักษร ข้อกำหนดล่าสุดจากผู้ใช้และโค้ด THE_X ปัจจุบันมีลำดับความสำคัญสูงกว่า

> เอกสารต้นทางมีคำอธิบายที่ไม่ตรงกันบางจุด รวมถึงตัวอย่างการตั้งค่าระบบและข้อมูลบัญชี จึงไม่คัดลอกข้อมูลส่วนตัวหรือ secrets มาที่นี่ เวลาพัฒนาให้ตรวจข้อกำหนดกับผู้ใช้และโค้ดจริงอีกครั้ง

## 1. เป้าหมายและขอบเขตของต้นแบบ

- เน้นผู้ใช้รถจักรยานยนต์ตั้งแต่ 150cc ถึง Bigbike ให้ประเมินอาการเบื้องต้นจากคำถามแบบข้อความ รับคำแนะนำการดูแล และเชื่อมต่อบริการซ่อมเมื่อเรื่องซับซ้อน คำตอบ AI เป็นคำแนะนำเบื้องต้น ไม่ใช่คำวินิจฉัยแทนช่าง (บท 1 §§1.1–1.3)
- เว็บแอปของ THE_ONE ใช้ Django Template, Tailwind CSS, Alpine.js, HTMX; Django/DRF เป็น business logic และ API; PostgreSQL + pgvector เก็บข้อมูลธุรกิจ/ฐานความรู้; n8n รับ webhook และประสาน embedding, vector retrieval, Gemini; Docker Compose ใช้รันระบบ, ngrok ใช้เป็น tunnel ทดสอบ (บท 1 §1.3, บท 3 §3.1)
- สถาปัตยกรรมอธิบายเป็น modular monolith/3-tier: presentation → Django/API → PostgreSQL/pgvector และบริการ AI ผ่าน n8n (บท 3 §3.1)
- ตรวจภาพ 3.1 แล้ว: Browser ↔ Django ↔ PostgreSQL; Django เชื่อม n8n ซึ่งต่อฐานข้อมูลและ Gemini ด้วย ส่วนภาพ 3.16 แสดง use case ของลูกค้า/ช่าง/Admin และ n8n ตามบทบาทข้างล่าง
- กลุ่มบทบาท: ผู้เยี่ยมชม, ลูกค้า, ช่าง, ผู้ดูแลระบบ ระบบต้องใช้ได้หลายอุปกรณ์และเอกสารระบุเป้าหมายอย่างน้อย 50 ผู้ใช้ แต่ไม่ได้แสดงหลักฐาน load test ในส่วนที่อ่าน (บท 3 §3.2)

## 2. เส้นทางผู้ใช้และหน้าจอ

| ผู้ใช้ | พฤติกรรมในต้นแบบ | แหล่งในรายงาน |
| --- | --- | --- |
| ผู้เยี่ยมชม | ดูหน้าแรก/ข้อมูลแนะนำ สมัครโดยเลือกประเภทลูกค้าหรือช่าง แล้วเข้าสู่ระบบ | §3.3 ภาพ 3.2–3.4; ภาคผนวก ค §§ค.1.1–ค.1.3 |
| ลูกค้า | แก้โปรไฟล์/รูป เพิ่มรถ เลือกรถ ประเภทงาน อาการ วันเวลา จอง ดูสถานะ/ประวัติ ยกเลิก แชทช่าง ถาม AI ดูการแจ้งเตือน | §3.3 ภาพ 3.6–3.14; บท 6 §6.1; ภาคผนวก ค §ค.2 |
| ช่าง | แก้โปรไฟล์ ดู Dashboard/คิว รับหรือปฏิเสธงาน เริ่มซ่อม ปิดงาน แชทลูกค้า ดูการแจ้งเตือน | §3.3 ภาพ 3.5, 3.9, 3.15; บท 6 §6.1; ภาคผนวก ค §ค.3 |
| Admin | ใช้ Django admin จัดการบัญชี/บทบาท รถ การจอง งานช่าง ห้องแชท การแจ้งเตือน ฐานความรู้ และ n8n workflow | ภาคผนวก ค §ค.4 |

รายละเอียด UI จากคำบรรยายภาพและคู่มือในต้นทาง:

- หน้าแรกมีทางเข้า AI Chatbot และจองคิว การ์ดฟีเจอร์หลัก 3 ส่วน และแถบนำทางที่มี badge ข้อความค้างอ่าน/แจ้งเตือน พร้อมเมนูโปรไฟล์ (ภาคผนวก ค §ค.1.1)
- สมัครสมาชิกมี username, email, ชื่อ, นามสกุล, รหัสผ่าน/ยืนยัน, โทรศัพท์, รูปโปรไฟล์; หน้า login มีปุ่มแสดง/ซ่อนรหัสผ่าน (ภาคผนวก ค §§ค.1.2–ค.1.3) **THE_X ปัจจุบันใช้ flow สมัครและกู้รหัสผ่านตามคำสั่งใหม่ของผู้ใช้ ไม่ย้าย flow อีเมลจากต้นแบบกลับมาเอง**
- รถในต้นแบบระบุยี่ห้อ รุ่น ทะเบียน ปี ซีซี และหมายเหตุ; หน้ารายการแสดงเป็นการ์ดและลบรถได้ (ภาคผนวก ค §ค.2.1)
- การจองต้นแบบ: เลือกรถ ประเภทบริการ คำอธิบาย วันอนาคต ช่วงเวลา และหมายเหตุ; รายการกรองตามสถานะและแสดงปุ่มแชทเมื่อช่างรับงาน (ภาคผนวก ค §§ค.2.2–ค.2.3)
- แชทมีรายการห้องเรียงข้อความล่าสุด แสดงผู้สนทนา เวลา รถ/เลขจอง badge ยังไม่อ่าน; ห้องแสดง bubble ของตนเองทางขวา อีกฝ่ายทางซ้าย และ polling ทุก 2 วินาที (ภาคผนวก ค §ค.2.5)
- แจ้งเตือนมีรายการอ่าน/ยังไม่อ่าน badge และลิงก์ไปงาน/แชท; ช่างมี dashboard สถิติงานกับตัวกรองสถานะ (ภาคผนวก ค §§ค.2.7, ค.3.1)

## 3. วงจรงานซ่อมและสิทธิ์

1. ลูกค้าสร้างการจอง → `pending`; บท 3 §3.6.1 ระบุให้ส่งการแจ้งเตือนไปยังช่างที่พร้อมทำงาน
2. ช่างรับงาน → `confirmed` ใน THE_ONE, กำหนดช่างและสร้างห้องแชทอัตโนมัติ แล้วแจ้งลูกค้า (บท 3 §3.6.2; บท 4 §4.5; ภาคผนวก ค §ค.3.2)
3. ช่างเจ้าของงานเริ่มซ่อม → `in_progress` และปิดงาน → `completed`; ทั้งสองขั้นแจ้งลูกค้า (ภาคผนวก ค §§ค.3.3–ค.3.4)
4. การยกเลิก → `cancelled`; ต้นทางมีคำอธิบายไม่ตรงกัน: บท 4 §4.3.2 บอกยกเลิกได้เมื่อ `pending` หรือ `confirmed` แต่ภาคผนวก ค §ค.2.3 ระบุปุ่มยกเลิกเฉพาะ `pending` ต้องตัดสินกติกาตาม THE_X ไม่ใช่อนุมานจากต้นแบบ
5. ทุกการอ่าน/ส่งข้อความและการเปลี่ยนสถานะต้องตรวจผู้มีสิทธิ์ตามเจ้าของงาน/ช่างที่รับงาน; บท 3 §3.6.3 กล่าวถึง `is_read` และ unread count ส่วนบท 6 §6.2 ยอมรับว่าการตรวจสถานะอย่างเดียวกันช่างรับงานพร้อมกันไม่พอ และเสนอ database locking

## 4. AI และฐานความรู้

- คำถามข้อความจากลูกค้า → Django API → n8n webhook → ค้นฐานความรู้ PGVector → Gemini → ส่งคำตอบกลับ; บท 4 §4.7 ระบุ field `output` ในคำตอบ webhook และ fallback แบบจับ keyword เมื่อ n8n ใช้ไม่ได้
- ต้นทางเสนอข้อมูลจากเว็บ/ชุมชนและคู่มือเทคนิคโดยคัดความน่าเชื่อถือก่อนใช้งาน (§1.3); บท 6 §6.2 กล่าวถึง batch embedding, cosine similarity และ IVFFlat ส่วน §6.3 เสนอ HNSW/ขยายข้อมูลในอนาคต สิทธิ์ใช้งานและคุณภาพแหล่งข้อมูลต้องตรวจแยกก่อน ingest
- AI ตอบเรื่องอาการ การบำรุงรักษา และค่าซ่อมโดยประมาณ แต่ต้องสื่อความไม่แน่นอนและแนะนำให้ช่างตรวจจริง (ภาคผนวก ค §ค.2.4)
- ข้อกำหนดคุณภาพที่รายงานระบุคือรอ AI ไม่เกิน 30 วินาทีแล้ว fallback; ข้อจำกัด rate limit/ค่าใช้จ่ายของ provider และคุณภาพคำตอบเป็นความเสี่ยงที่ต้องวัดในการทำ THE_X (บท 6 §§6.1–6.3)

## 5. แบบจำลองข้อมูลจากต้นแบบ

บท 3 §3.7 มี ERD และ data dictionary อย่างน้อย `User`, `Admin`, `Mechanic`, `Booking`, `Notification`, `ChatRoom`, `Message`; ในคำอธิบายบทอื่นยังมี `Motorcycle`, `KnowledgeBase`, `ChatHistory`, `WorkQueue` ไม่ควรถือว่ารายการ D1–D7 เป็น schema ครบทั้งระบบ

ตรวจภาพ 3.17 (class diagram) แล้วเห็นคลาส `User`, `MechanicProfile`, `Motorcycle`, `Booking`, `Notification`, `WorkQueue`, `Review`, `ChatRoom`, `Message`, `KnowledgeBase`, `ChatSession`, `ChatMessage` และองค์ประกอบ n8n/Gemini/PGVector; ภาพ 3.22 (ERD) แสดงเพียง 7 entity ตาม data dictionary จึงเป็นภาพคนละระดับรายละเอียด ไม่ใช่ schema สองชุดที่นำมารวมได้ทันที

- `User`: username, password hash, email, ชื่อ, โทรศัพท์, active, mechanic flag, เวลาใช้งาน, รูป
- `Mechanic`: user, ทักษะ, ประสบการณ์, bio, ความพร้อมรับงาน
- `Booking`: customer, mechanic, service type, อาการ, status, วันจอง/นัด/เสร็จ, เหตุผลยกเลิก, ราคา, สถานที่, ห้องแชท
- `Notification`: ผู้รับ, ประเภท, ข้อความ, เวลา, อ่านแล้ว
- `ChatRoom`/`Message`: ผูกห้องกับงานหนึ่งรายการ, ข้อความ, ผู้ส่ง, เวลา และสถานะอ่าน ตามคำอธิบาย sequence

ข้อควรตรวจเมื่อออกแบบ THE_X: ราคาไม่ควรใช้ float สำหรับเงิน; `is_mechanic` flag เดี่ยวไม่พอสำหรับสมาชิกหลายร้าน; การลบข้อมูลที่มีประวัติการจองต้องมีนโยบายเก็บประวัติ; แชท/โปรไฟล์มีข้อมูลส่วนบุคคลจึงต้องกำหนดสิทธิ์และ retention

## 6. การทดสอบและข้อจำกัดที่รายงานกล่าวถึง

บท 5 แบ่งการทดสอบเป็นสมัคร/เข้าสู่ระบบ/ออก, โปรไฟล์, รถ, จอง, dashboard และงานช่าง, แชท, AI, แจ้งเตือน, รีเซ็ตรหัสผ่าน; ตาราง 5.1–5.15 เป็นหลักฐานในรายงาน ไม่ใช่หลักฐานว่าฟังก์ชัน THE_X ผ่านแล้ว

ปัญหาที่ต้นทางยอมรับในบท 6 §6.2: AI ช้า/อาจ timeout, ช่างรับงานชนกัน, การจองซ้ำ, ตั้งค่า pgvector, สร้างห้องแชท, ingest ความรู้จำนวนมาก, แจ้งเตือนยังไม่ real-time, และ API rate limit ส่วน roadmap §6.3 คือ WebSocket/Push, calendar slot, ปรับ RAG, mobile app, การชำระเงิน และ admin analytics สิ่งเหล่านี้เป็น **ข้อเสนออนาคตของ THE_ONE** ไม่ใช่งานที่ THE_X อนุมัติแล้วทั้งหมด

## 7. จับคู่กับ THE_X ณ วันที่อ่าน

ตรวจเทียบจาก `README.md`, `backend/garage/models.py`, `backend/garage/bookings.py`, `backend/garage/chat.py`, `backend/garage/ai_chat.py` และเอกสารขอบเขตใน repo เท่านั้น ยังไม่ได้รัน E2E ใหม่เพื่อรับรองสถานะ deploy จริง

| หัวข้อ | THE_X ในโค้ด/คู่มือปัจจุบัน | ผลต่อการอ้างอิงต้นแบบ |
| --- | --- | --- |
| UI/บัญชี | Flutter Web + Django OIDC Authorization Code/PKCE; role ผ่าน Django groups; session แยกแท็บ | คง OIDC และ Flutter ตาม THE_X; ไม่ย้าย Django Template/JWT session จาก THE_ONE |
| โดเมนร้าน | `Shop` มีสมาชิกช่าง รูป ที่อยู่ หมุด และสถานะรับจอง; ลูกค้าเลือก **ร้าน** ก่อนจอง | ต้นแบบเป็นคิวช่างกลาง ต้องแปลงทุก flow ให้เป็นร้านและตรวจ membership |
| การจอง | `Booking` ผูกร้าน/รถ/ช่าง; `pending → accepted → in_progress → completed`, หรือ `cancelled`; ใช้ transaction/row lock และ unique active booking ต่อรถ | แมป `confirmed` ของ THE_ONE เป็น `accepted`; กติกา duplicate/cancel ให้ยึดโค้ด THE_X จนกว่าจะมีคำสั่งเปลี่ยน |
| แชท | `ShopConversation` ผูกลูกค้า+ร้าน, `ShopMessage` เก็บข้อความใน PostgreSQL; Flutter refresh ทุก 8 วินาที | THE_ONE ผูกห้องกับใบจองและ refresh 2 วินาที; เป็นคนละโมเดล ห้ามสันนิษฐานว่ามี unread/read receipts แล้ว |
| AI | `backend/garage/ai_chat.py` รองรับ webhook HTTPS ฝั่ง server; README ระบุยังต้องตั้งค่า n8n/AI จริง | แยกสัญญา JSON ของ THE_X (`message`/`reply`) จาก `output` ใน THE_ONE; ยังไม่มีหลักฐานว่า RAG/pgvector ทำงานใน THE_X |
| Deploy | Docker demo และ ngrok ตาม README; production ถาวรยังเป็นงานภายหลัง | ใช้ข้อมูล THE_ONE เพื่อวางแผนเท่านั้น ไม่ถือว่า production-ready |

## 8. หลักการใช้ต้นแบบในการพัฒนาต่อ

1. อ้างเลขบท/ภาพ/ภาคผนวกด้านบนเมื่อเสนอฟีเจอร์ เพื่อแยก “พบใน prototype” จาก “ผู้ใช้สั่งทำใน THE_X”
2. ตรวจ implementation จริง, migration และ tests ของ THE_X ก่อนเปลี่ยน schema/API/UI; ปรับเฉพาะส่วนที่เข้ากับร้าน, OIDC และบทบาทปัจจุบัน
3. ก่อนขยาย AI ให้ตกลงแหล่งความรู้, สิทธิ์ใช้ข้อมูล, retrieval/evaluation, webhook contract, timeout และการไม่เปิดเผยข้อมูลส่วนตัว
4. ก่อนปรับการจอง/แชท ให้กำหนด state transition, สิทธิ์ลูกค้า/ช่าง/ร้าน, concurrency, การแจ้งเตือน และนโยบายเก็บข้อมูลให้ชัด
5. ไม่ใช้ตัวอย่างการรีเซ็ตรหัสผ่านตรงจากรายงานเป็นมาตรฐานความปลอดภัย; flow บัญชีใน THE_X ต้องได้รับการทบทวนก่อนนำออกสาธารณะ
